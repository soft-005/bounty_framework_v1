Here’s a **real-world, practical checklist** that bug bounty hunters actually use when reporting on **HackerOne, Intigriti, Bugcrowd, etc.** — not theory, but stuff that helps reports get **accepted, triaged fast, and paid**.

---

## 1. Before You Even Report (Pre-Submission)

### ✅ Program & Scope Check

* [ ] Target is **in scope** (domain, app, API, version)
* [ ] Vulnerability type is **allowed**
* [ ] You’re following **safe harbor rules**
* [ ] No automated scanning if disallowed
* [ ] You didn’t touch real user data unnecessarily

> 🚩 30% of reports get closed just for being out of scope

---

### ✅ Duplicate Check

* [ ] Search program’s **disclosed reports**
* [ ] Check similar endpoints/features
* [ ] Verify bug still exists **right now**

---

## 2. Validate the Bug (This Is Critical)

### ✅ Reproducibility

* [ ] Bug works **100% consistently**
* [ ] Works in a **clean browser / fresh account**
* [ ] Works without dev tools magic or assumptions
* [ ] Works without race-condition luck (unless that’s the bug)

---

### ✅ Impact Confirmation

* [ ] Can you:

  * Read/modify/delete data?
  * Access another user’s account?
  * Bypass auth or permissions?
  * Execute JS (XSS)?
  * Control business logic?
* [ ] Impact matches program’s **severity definitions**

> If you can’t explain impact clearly, triage will downrank it.

---

## 3. Evidence Collection

### ✅ Proof of Concept (PoC)

* [ ] Minimal steps — **no fluff**
* [ ] Clear payloads / requests
* [ ] Works without editing anything mid-step

---

### ✅ Screenshots / Videos

* [ ] Screenshots show:

  * URL
  * Account role (user/admin/etc.)
  * Result clearly
* [ ] Video preferred for:

  * Auth bypass
  * IDOR
  * Race conditions
  * Multi-step exploits

---

### ✅ Requests & Responses

* [ ] Include:

  * HTTP method
  * Endpoint
  * Headers (redact tokens)
  * Body
  * Response
* [ ] Use Burp / curl / Postman output

---

## 4. Writing the Report (This Matters More Than the Bug)

### ✅ Title (Very Important)

* [ ] Short
* [ ] Precise
* [ ] Includes impact

**Good:**

> `IDOR allows viewing other users’ invoices`

**Bad:**

> `Security issue on invoices page`

---

### ✅ Summary

* [ ] 2–4 sentences max
* [ ] What the bug is
* [ ] Who is affected
* [ ] Why it matters

---

### ✅ Steps to Reproduce

* [ ] Numbered steps
* [ ] Copy-paste friendly
* [ ] Assume triager is tired and rushed
* [ ] Include example IDs / payloads

---

### ✅ Impact Section (Most Important)

* [ ] Real-world consequence
* [ ] Business risk (not just technical)
* [ ] What an attacker could do at scale

Example:

> An attacker can enumerate user IDs and download invoices belonging to any customer, exposing PII and financial data.

---

### ✅ Suggested Fix (Optional but Helpful)

* [ ] Authorization check
* [ ] Object ownership validation
* [ ] Rate limiting
* [ ] Input sanitization

---

## 5. Submission Hygiene

### ✅ Tone & Professionalism

* [ ] Polite
* [ ] Neutral
* [ ] No threats, no bragging
* [ ] No “this is critical pls pay high”

---

### ✅ Redactions

* [ ] Remove:

  * Tokens
  * Passwords
  * Cookies
* [ ] Use placeholders like `REDACTED_TOKEN`

---

## 6. After Submission

### ✅ Triage Phase

* [ ] Respond quickly to questions
* [ ] Clarify calmly
* [ ] Provide extra PoC if asked
* [ ] Don’t argue severity emotionally

---

### ✅ If Marked Informative / N/A

* [ ] Re-read program policy
* [ ] Ask **one** clarification question (politely)
* [ ] Learn and move on

> Fighting triage almost never helps.

---

## 7. Platform-Specific Tips

### HackerOne

* Strong focus on **impact**
* Loves clear **step-by-step**
* Duplicate detection is strict

### Intigriti

* Very picky about **scope**
* Likes **clean reports**
* Fast triage if well written

### Bugcrowd

* Likes **technical depth**
* Strong emphasis on **reproducibility**

---

## 8. Final “Golden Rule” Checklist

Before clicking **Submit**, ask:

* [ ] Can someone reproduce this in 5 minutes?
* [ ] Is impact obvious without security knowledge?
* [ ] Would *I* understand this report if I were the company?

If yes → submit 💰

Below is a **practical Python script** that takes **raw bug-hunting notes** and converts them into a **high-quality bug bounty report** using a structure modeled after **real accepted HackerOne / Intigriti reports**.

This is meant to be:

* CLI-friendly
* Easy to customize
* Focused on **clarity, impact, and triage acceptance**

---

## What This Script Does

Input:

* Messy notes (payloads, endpoints, observations)

Output:

* Clean report with:

  * Title
  * Summary
  * Steps to Reproduce
  * Impact
  * Proof of Concept
  * Suggested Fix

---

## Example Usage

```bash
python report_generator.py notes.txt
```

---

## Python Script: `report_generator.py`

```python
import sys
from textwrap import dedent

TEMPLATE = """
Title:
{title}

Summary:
{summary}

Steps to Reproduce:
{steps}

Proof of Concept:
{poc}

Impact:
{impact}

Suggested Fix:
{fix}
""".strip()


def generate_title(notes):
    if "idor" in notes.lower():
        return "IDOR allows unauthorized access to other users' data"
    if "xss" in notes.lower():
        return "Stored XSS allows execution of arbitrary JavaScript"
    if "auth" in notes.lower():
        return "Authentication bypass allows unauthorized access"
    return "Unauthorized action due to missing authorization checks"


def generate_summary(notes):
    return (
        "An authorization vulnerability was identified where a user can perform "
        "actions on resources they do not own. This occurs due to missing or "
        "insufficient access control checks on the backend."
    )


def generate_steps(notes):
    steps = [
        "1. Log in as a low-privileged user.",
        "2. Intercept the request using a proxy (Burp / similar).",
        "3. Modify the resource identifier in the request.",
        "4. Forward the request to the server.",
        "5. Observe that unauthorized data is returned."
    ]
    return "\n".join(steps)


def generate_poc(notes):
    return dedent("""
    Example Request:

    GET /api/v1/resource/12345 HTTP/1.1
    Host: target.com
    Authorization: Bearer REDACTED

    Example Response:
    HTTP/1.1 200 OK
    {
        "user_id": "12345",
        "email": "victim@example.com"
    }
    """).strip()


def generate_impact(notes):
    return (
        "An attacker can enumerate resource identifiers to access sensitive data "
        "belonging to other users. This could lead to exposure of personal data, "
        "account takeover vectors, or regulatory compliance issues depending on "
        "the affected endpoint."
    )


def generate_fix(notes):
    return (
        "Ensure that the backend validates ownership of the requested resource "
        "for the authenticated user. Implement proper authorization checks and "
        "avoid relying on client-supplied identifiers."
    )


def main():
    if len(sys.argv) != 2:
        print("Usage: python report_generator.py <notes.txt>")
        sys.exit(1)

    with open(sys.argv[1], "r", encoding="utf-8") as f:
        notes = f.read()

    report = TEMPLATE.format(
        title=generate_title(notes),
        summary=generate_summary(notes),
        steps=generate_steps(notes),
        poc=generate_poc(notes),
        impact=generate_impact(notes),
        fix=generate_fix(notes),
    )

    print("\n" + "=" * 60 + "\n")
    print(report)
    print("\n" + "=" * 60 + "\n")


if __name__ == "__main__":
    main()
```
